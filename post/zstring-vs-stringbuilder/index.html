ZString vs StringBuilder

· 2026-07-29 · # 字符串 # Unity

Unity：ZString vs StringBuilder 选型完整对比

先给核心结论：

频繁拼接、循环内大量字符串操作：优先 ZString；简单少量拼接、老旧平台/不想引入包：用 StringBuilder。
ZString 本质是新一代高性能字符串库，底层基于 Utf16 缓冲，性能普遍优于原生 StringBuilder，是目前 Unity 社区首选方案。

一、两者基础定位

1. StringBuilder（.NET 原生，无第三方包）

命名空间：System.Text.StringBuilder

  • .NET 官方自带，不需要导入任何插件
  • 原理：维护一个 char[] 缓冲区，避免每次 + 创建新 string
  • 局限：
    1. 扩容策略保守，频繁扩容产生 GC
    2. AppendFormat、插值拼接性能一般
    3. 大量微小拼接、循环嵌套场景 GC 压力明显
    4. 不支持直接写入 Span<char> / 更低分配的API

2. ZString（第三方开源库，Cysharp/ZString）

仓库：https://github.com/Cysharp/ZString

专为 .NET / Unity 优化的零分配字符串工具，兼容 IL2CPP

  • 提供：ZStringBuilder、ZString.Format、插值字符串 ZInterpolatedStringHandler
  • 优势核心：大量场景可以做到近乎 0 GC，比原生 StringBuilder 更快、更少堆分配
  • 注意：需要导入包；支持 Unity 2020+，全平台（Windows/Android/iOS/WebGL IL2CPP）

二、性能关键差异（Unity IL2CPP 环境实测共识）

  1. 简单循环字符串拼接
    • 少量拼接：两者差距不大
    • 上百次循环、Update持续拼接、日志批量组装：ZStringBuilder GC 远低于 StringBuilder
  2. 格式化字符串（最拉开差距场景）
    // 原生：大量装箱、GC
string s1 = string.Format("Pos:{0},{1},{2}",x,y,z);
// ZString：无装箱
string s2 = ZString.Format("Pos:{0},{1},{2}",x,y,z);
    ✅ 格式化场景 ZString 碾压原生 StringBuilder + string.Format
  3. 字符串插值（C# 10+）
    // 普通插值会产生GC
var str = $"X:{x} Y:{y}";
// ZString 专用插值处理器，零分配构建
var str = ZString.CreateStringBuilder().Append($"X:{x} Y:{y}").ToString();
  4. 复用对象
    • StringBuilder 可以 Clear() 复用；
    • ZStringBuilder 同样支持 Clear，并且内部缓冲复用策略更高效；还提供 ZStringBuilderPool 对象池进一步降低GC。

三、分场景选型建议

✅ 推荐选用 ZString 的情况

  1. Update / FixedUpdate 每一帧都执行字符串拼接、格式化（UI文本、战斗日志、坐标打印）
  2. 大量循环内组装字符串（批量生成描述、任务文本、列表内容）
  3. 高频日志打印（替代 Debug.Log 封装 ZString 日志，消除格式化GC）
  4. 大量数值转字符串、坐标拼接、格式化输出
  5. IL2CPP 打包，追求极致性能、降低卡顿

标准写法示例

// 使用对象池，减少实例化开销
using var sb = ZStringBuilderPool.Get();
sb.Append("Player:")
  .Append(name)
  .Append(" HP:")
  .Append(hp);
string result = sb.ToString();
ZStringBuilderPool.Return(sb);

✅ 使用原生 StringBuilder 的场景

  1. 项目不允许引入第三方库（规范限制、精简包体积）
  2. Unity 版本过低（<2020，ZString兼容性差）
  3. 字符串操作非常少，仅偶尔一次性拼接，性能无关紧要
  4. 跨平台特殊兼容，不想额外引入外部代码维护成本

原生 StringBuilder 最佳实践

// 预先设置容量，避免频繁扩容！非常关键
var sb = new StringBuilder(256); 
sb.Append("A").Append("B");
var str = sb.ToString();
sb.Clear(); // 可复用

四、避坑重点

1. 不要混用误区

❌ 不要频繁 new StringBuilder() / new ZStringBuilder() 不回收；能用池尽量用池。
❌ 不要直接大量 string + "abc"，不管哪个库，原生字符串加法最差。

2. WebGL 注意

ZString 在 WebGL IL2CPP 完全兼容；但极个别老旧 .NET 后端环境无优势，Unity 客户端不用担心。

3. 内存警告

ZString.ToString() 依然会创建最终字符串对象（C# string不可变，无法规避）；
它优化的是中间过程GC，不能做到完全无字符串分配，只是大幅减少临时垃圾。

五、极简总结清单

场景 选择
帧循环高频拼接、格式化、战斗/UI文本 ZString (ZStringBuilder + 对象池)
偶尔少量拼接、禁止导入第三方插件 StringBuilder
大量 string.Format / 插值格式化 优先 ZString.Format
新手快速开发、不想配置包 StringBuilder

补充建议

如果你项目目前没有任何字符串优化库，直接导入 ZString，是当前 Unity 行业通用最优方案；
如果受项目管制不能加外部源码，则规范使用 StringBuilder，并初始化时预分配容量减少GC。
